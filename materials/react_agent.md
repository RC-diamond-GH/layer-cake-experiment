# 响应式 agent

我设想了一种响应式agent，我将用 3 个例子说明它的价值：

试想一个能玩minecraft的agent，它现在要用熔炉烧一些铁锭，然后制作一套铁甲，它调用了工具，把煤炭和粗铁放到了熔炉中，然后，熔炉烧铁锭需要时间，它该如何在烧完铁锭之后及时响应，然后制作铁甲呢？现有的ReAct，只能一遍遍轮询熔炉的状态，或者根据“烧一个物品需要15秒”来为自己调用“睡眠”工具，但我设想的响应式agent，它在把物品放到熔炉里之后，就会在熔炉上加一个事件订阅，熔炉完成烧制后，就会通过该订阅通知对应的agent

试想一个试图伪装成群组成员的群组机器人，我希望在群组里的成员讨论的过程中，讨论的内容可以主动传给 AI Agent，然后 AI Agent 会自行判断要不要发言，如果要发言，它就进行工具调用，这个过程中，群组与 AI Agent 之间是全双工通信，AI Agent 会主动向群组进行通信，群组也会主动向 AI Agent 进行通信。而现在有一些机器人框架，把群组功能做成了 MCP，然后直接接入任何一个支持 MCP 的 Agent 客户端，但这本质上是半双工通信，依然需要 Agent 主动调用 MCP 里的工具来获取群组信息。

试想一个 Agent 软件开发团队，团队里有三类角色，Manager, Worker, Reviewer。Manager 负责与我交流，澄清思路，规划任务；Worker 负责干活；Reviewer 负责代码审计。然而，三类角色之间的交互，有明确的监听事件的需求：Manager 会创建 Worker。Worker 拥有一个自己可以完全访问的 Worktree，它写完一批代码之后，会提交 PR，提交 PR 时，有一个流程：跑 CI、过 Code Review、合并、跑 CI，如果第一次 CI 失败，那么这就是一个需要驱动给 Worker 的事件，Code Review 不通过，也是一个需要通知给 Worker 的事件，最后的 CI 亦然，直到最后的 CI 也通过，这个 Worker 才能被归档。而 Reviewer 也一样，有新的通过 CI 的 PR 来了之后，它就要开始实施 Code Review 了，它会检查代码是不是有安全问题，性能问题，测试有没有放水。可以说，我设想的这套系统，中间有好几个环节，都依赖于事件响应。

我设想的是一种“精神分裂Agent”，当一个事件通知给一个 Agent，那么它立刻从上一个上下文中“分裂”一个上下文出来，用这个通知作为提示词来启动推理，并根据一个我目前并不着急提出的条件来执行“精神整合”

同时修改一个状态的问题确实可能存在，但这个问题的解决，也确实很难靠“精神分裂”模型本身，我的设想是把“资源”这个概念定义好，然后给出“锁”的概念——要么同时有一个写锁，要么同时有多个读锁，当然，这是基本的框架成型之后再考虑的事情

其实“锁”本身和这个响应式 Agent 系统也能有所关联，比如，一个 agent 想要编辑 auth.ts，就必须先给 auth.ts 挂写锁，但此时上面有3个读锁，而此时它可以挂“授予写锁”事件订阅，然后自己就会挂起，auth.ts 上的锁全部释放之后，它就会触发这个订阅，从而唤醒这个 agent
