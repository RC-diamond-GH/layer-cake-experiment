# Layer Cake MVP 执行文档

版本：0.4，待审阅。日期：2026-11-09。

目标：提供一组可复用的 Agent 组件，能够编写实验、控制执行、查看上下文和调用记录，并比较不同机制。

已确认：Rust 实现机制并运行实验；Lean 4 探索及证明机制性质。同一机制的两份代码由用户或 AI 审阅，确认约定范围内的等价性。

以下对象、接口和实施顺序是本稿提出的方案，供逐项审阅。

实施分两阶段：先通过 ReAct 建立基础组件和观察装置，再以响应式 Agent 做一次扩展实验。第二阶段的任务包含发现、设计和验证新增抽象，并记录哪些基础组件得到了复用、哪些需要修改。

## 1. 先确定实验使用的对象

| 对象 | 保存什么、负责什么 | 与其他对象的关系 |
| --- | --- | --- |
| `ModelClient` | 模型 API 的调用接口 | 接收上下文快照和生成参数，返回模型输出或调用错误 |
| `LLMContext` | 系统提示词、全局材料、消息历史、可见工具定义 | 由 Agent 更新，模型读取快照，CLI 和报告查看版本 |
| `Tool` | 工具定义及执行接口 | 模型生成工具调用，Agent 选择对应工具执行 |
| `ToolRegistry` | 工具名称到可执行工具的映射 | 为上下文提供工具定义，为调用提供执行对象 |
| `ReAct` | 上下文、模型引用、工具注册表、轮次和执行状态 | 按生成、执行工具、更新上下文的顺序运行 |
| `Experiment` | 一段 Rust 装配代码及其配置 | 创建 Agent、模型、工具和环境，并提供运行入口 |
| `Run` | 一次实验的配置、控制句柄、对象索引和运行记录 | CLI 操作的主要对象；关联本次上下文和调用 |
| `CallRecord` | 一次模型或工具调用的输入、输出、错误及关联 ID | 模型调用关联上下文版本，工具调用关联提出它的模型输出 |

其中 `ModelClient`、`Tool` 使用 trait；`LLMContext`、`CallRecord` 使用数据结构；第一种 Agent 直接实现为具体的 `ReAct` 类型。Agent 公共接口在出现更多结构后提炼。

## 2. 按依赖关系实现基础组件

### 2.1 模型接口与上下文

因为实验需要调用 LLM，先定义 `ModelClient` 的异步生成接口。输入包含 `LLMContext` 快照和生成参数；输出包含回答、工具调用、停止原因和可获得的用量。调用失败通过错误分支返回。

先实现一个真实 API 适配器，以及一个按指定条件返回结果的脚本适配器。真实 API 的提供方和接口格式在审阅时选定；脚本适配器用于复现控制逻辑。

上下文字段参考现有 [LLM API 建模](./llm_api_model.md)。每个上下文具有 ID 和版本号。Agent 负责修改上下文，模型调用和观察器读取快照。每次调用保留实际使用的版本，之后修改上下文仍能查到旧输入。

“共享”落实为同一个上下文身份被 Agent、调用记录和观察器引用。首版由 Agent 单方写入；CLI 输入通过实验控制器在执行边界写入。

### 2.2 工具接口与注册表

因为模型输出可能包含工具调用，需要 `Tool` trait 提供两项能力：取得模型可见的定义，执行参数并返回结果或错误。

`ToolRegistry` 保存可执行工具。Agent 从中选择可见工具，生成 `LLMContext` 中的工具定义；执行时检查名称和可见集合，再分派调用。这样，展示给模型的定义和实际执行对象有明确对应。

先实现读取内存值、修改内存值两个测试工具，用来跑通查询和修改状态的过程。工具参数、结果及错误均保存到 `CallRecord`。

### 2.3 最简单的 ReAct

模型和工具可用后，实现一个具体 ReAct：

1. 取得上下文快照，调用模型并记录结果。
2. 将模型回答及工具调用追加到上下文。
3. 有工具调用时，按输出顺序执行，将结果逐项写回上下文。
4. 正常生成结束且没有工具调用时，结束本次任务。
5. 调用失败、生成截断、轮次耗尽分别报告原因。

首版将“一次生成及其工具结果写回”定义为一轮，轮与轮之间可以暂停。ReAct 是第一个完整使用基础组件的实验，用来检查这些接口是否够用。

### 2.4 记录入口

在模型和工具的公共调用入口记录请求、结果、错误和耗时。Agent 另外报告状态变化、上下文版本和等待原因。

记录至少带运行 ID、对象 ID、记录 ID、调用关联和产生顺序。存在明确触发原因时保存对应记录 ID，便于从一次动作追查到输入。

运行对象索引支持登记实验自定义的对象种类。观测记录共用身份、来源和关联字段，具体内容由实验定义；CLI 和报告至少能展示这些字段与内容。`CallRecord` 是调用观测的具体形式。后续增加资源、订阅等对象时，可以沿用这个观察入口。

一次运行保存配置、记录、上下文快照和结果摘要。先使用本地文件。报告从这些文件生成。

## 3. 实验作者编写什么

作者用 Rust 编写装配函数，选择模型、工具、Agent 实现和环境，并返回本次实验的执行入口与控制句柄。普通参数放入配置文件。

例如，第一份实验装配一个 ReAct、一个脚本模型和两个工具。换成真实模型时替换模型配置；研究新的驱动机制时编写新的控制器，并复用上下文、模型、工具及记录组件。

实验返回的控制句柄声明支持哪些操作，接收继续、步进、暂停、停止及实验自定义输入。控制器决定这些操作在什么执行位置生效，并报告处理结果。

首版建议在同一个 Rust 程序中注册实验入口。独立进程接入、自动机公共 trait、插件加载安排在基础接口经过实际使用后评估。

## 4. CLI 操作哪些对象

CLI 启动一个 `Experiment`，得到一个 `Run`。后续控制针对这个运行；查询通过运行中的对象索引定位到上下文、Agent 观测和调用记录。

| 对象 | 可以进行的操作 | 操作结果 |
| --- | --- | --- |
| 实验定义 | 查看说明、配置项，选择配置启动 | 创建独立的运行及初始对象 |
| 运行 | 查看状态，继续、步进、暂停、停止 | 控制句柄处理请求，保存确认记录 |
| 上下文 | 查看最新快照或指定版本 | 展示提示词、消息和可见工具 |
| Agent 观测 | 查看最近报告的阶段、轮次、等待条件 | 同时显示观测产生的位置和时间 |
| 模型调用 | 查看输入快照、生成参数和完整返回 | 能定位到本轮具体依据 |
| 工具调用 | 查看参数、结果、错误和来源 | 能跳转到提出调用的模型输出 |
| 两次运行 | 比较配置、调用次数和上下文规模 | 生成比较摘要及详细报告 |

交互控制台持有当前运行。暂停发生在实验声明的执行边界；模型调用期间请求暂停，会等待当前边界完成。停止请求结束后续派发，并记录在途调用的实际结果或未知状态。

需要给 Agent 补充用户消息，或向环境注入事件时，CLI 将输入交给该实验的控制句柄。输入内容和生效位置进入运行记录。

静态 HTML 使用同一份记录，提供时间线、对象过滤和调用详情。运行中生成的报告标明记录截止位置，运行结束后生成完整报告。

## 5. 扩展实验：实现响应式 Agent，并提炼新增抽象

本阶段由执行者同时完成机制实现和抽象设计。以“启动一个耗时作业，完成后继续行动”为问题，使用模拟熔炉提供具体情境。熔炉只存在于这个实验的环境实现中。

### 5.1 从场景辨认对象

以下是执行者需要检验的候选划分，具体接口在实现过程中确定：

| 场景中的东西 | 候选抽象 | 职责与关系 |
| --- | --- | --- |
| 熔炉及其原料、燃料、产物 | 有状态的环境对象／资源 | 保存身份、状态和版本，提供查询及状态变更操作 |
| 启动烧制、查询进度、取出产物 | 工具 | 将环境对象的操作暴露给 Agent，复用已有 `Tool` 接口 |
| 某次烧制作业完成 | 事件 | 携带事件身份、来源、作业 ID 与结果，供执行过程处理 |
| 熔炉发布完成消息的能力 | 事件源 | 向订阅机制发布事件；事件源也可以由计时器等组件实现 |
| Agent 订阅某次作业的完成消息 | 订阅 | 保存事件源、匹配条件和接收者之间的关系，具有登记与取消操作 |
| 事件到达后继续工作 | 响应式驱动器 | 接收匹配事件，决定入队、唤醒、刷新上下文与继续生成 |

工具调用和事件订阅分别承担主动操作与接收变化的职责。例如，工具返回作业 ID，订阅用这个 ID 匹配完成事件，驱动器随后安排下一次模型调用。事件用于驱动执行；观测记录用于保存这次事件及处理过程。

### 5.2 执行者要交付什么

1. 实现具体熔炉环境和一个轮询版本，明确作业状态与完成条件。
2. 实现事件发布、订阅关系和接收队列，写清登记、取消、重复事件以及登记前已完成作业的处理规则。
3. 编写响应式控制器，复用模型、工具、上下文和记录组件。用模拟时钟控制事件发生顺序。
4. 为新增对象提供观测：能查看订阅绑定了谁、什么事件匹配成功、事件进入哪个队列，以及为什么触发模型调用。
5. 用一个简单计时器替换熔炉事件源，检查事件与订阅接口是否仍然可用，据此修正候选抽象。

至少检查完成早于订阅、重复通知、等待期间资源改变三种情况。记录应能追查事件、订阅、控制决定、上下文版本和模型调用之间的关系。

### 5.3 怎样判断平台帮助了扩展

执行者提交一份简短说明：复用了哪些组件，新增了哪些机制，修改了哪些原有接口，以及修改的原因。增加新的基础设施是这个阶段的预期产出。

判断依据是：模型接入与工具调用能否继续复用；新增资源和订阅是否能通过已有入口被观察；修改控制方式时，哪些地方因原先绑定 ReAct 而必须返工。发现限制后调整平台，并保留原因。

在确定性模拟实验上增加执行回放：用已保存的模型和工具返回驱动原实验，逐次检查请求是否匹配。发现差异就停止并定位分歧。回放使用模拟结果替代外部副作用。

## 6. Lean 4 配套工作

选择已经实现的一段机制，在 Lean 中写出状态、输入、转移和需要证明的性质。可先复用现有 [基础定义](../AgentTheory/Basic.lean) 和 [示例](../AgentTheory/Examples.lean)。

用户或 AI 对照 Rust 与 Lean 代码审阅，保存对应版本、状态与输入映射、适用假设、已证明性质和审阅结论。证明针对 Lean 定义，Rust 实现的对应关系由审阅确认。

## 7. 执行顺序与验收

| 顺序 | 本步交付 | 验收方式 |
| --- | --- | --- |
| 1 | 模型 trait、上下文、真实与脚本适配器 | 同一调用入口可以取得真实回答或指定返回 |
| 2 | 工具 trait、注册表、具体 ReAct | 完成生成、工具调用、结果写回的完整循环 |
| 3 | 上下文快照、调用记录、运行对象 | 能查清一次工具动作来自哪次生成、使用了什么输入 |
| 4 | CLI 控制与 HTML 查看 | 可以逐轮执行，检查上下文和调用，再继续运行 |
| 5 | 响应式扩展实验、资源与订阅等新增抽象、复用及改动说明 | 能追查事件如何触发生成；替换为计时器事件源后仍可使用订阅机制 |
| 6 | 比较、模拟回放、Lean 机制对照 | 能定位回放分歧，并完成一段机制的证明与代码审阅 |

每一步同时提供一份可以运行的样例。最终验收既检查实验行为，也审阅扩展过程中保留下来的组件、新增抽象和平台修改。

本稿收起了前版的文件布局、协议字段和命令命名；优先审阅对象关系、组件职责及上述执行顺序。进程接入调整为后续评估项，其余核心能力按表中顺序实现。
