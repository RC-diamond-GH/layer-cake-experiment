# 从四份构想到一条可以推进的研究与工程主线

这份整理依据四份文档的写作顺序：[LLM API 建模](./llm_api_model.md)、[Layer Cake](./layer_cake.md)、[上下文订阅](./context_subscribe.md)、[响应式 Agent](./react_agent.md)，并对照当前的 [Lean 基础定义](../AgentTheory/Basic.lean) 与 [示例](../AgentTheory/Examples.lean)。

以下是对这些构想的综合判断和建议，不是已经证明的理论，也不是已经实现的架构。Layer Cake 文档中提到的 Rust PoC 及测试情况，在当前工作区没有对应源码可供核验；本文把它们视为原文记录，并以你说明的“尚无 MVP”为当前工程状态。

## 1. 这些想法可以统一，但应当统一问题，而不是把所有机制塞进一个对象

我从四份文档中读到的共同问题是：

> 如何让一个由模型参与决策的执行过程，在环境不断变化时，获得适当的信息、在适当的时机继续工作，并且使继续执行的规则可以被理解和检查？

这里包含三个相互关联但不同的问题：

1. **看见什么**：模型此刻收到哪些历史、资源快照、工具和任务状态？
2. **何时运行**：什么输入使任务需要继续推理，什么时候应该等待？
3. **怎样继续**：沿用原执行过程、改变控制状态、委托子任务，还是构造后继实例？

四份文档分别深入了这些问题的不同部分。它们并非互相替代的四个框架，而可以成为同一系统的不同部件。

目前的混乱主要来自：一个构想还没有形成可检查的最小闭环，你就已经在为它设计通用扩展机制；随后出现的新需求，又被迫放入先前已经规定好的调度结构。于是“一个有价值的能力”与“实现这个能力的一整套架构”逐渐难以分开。

我建议把近期方向表述为：**研究并实现一个能够观察变化、等待事件、继续任务的 Agent 执行机制。** 智能自动机为它提供局部运行语义，Layer Cake 暂时作为承载这些实验的项目，而不必立即成为通用 Agent 开发框架。

## 2. 按写作顺序回看：每一步增加了什么

| 文档 | 当时解决的核心问题 | 值得保留的贡献 | 目前需要松动的假设 |
| --- | --- | --- | --- |
| [LLM API 建模](./llm_api_model.md) | 一次模型交互如何表示 | 请求、响应、工具调用的统一表示 | 一个对话对象可以承载全部运行事实；跨提供方完整一一映射 |
| [Layer Cake](./layer_cake.md) | 多种自动机如何组合、委托和重构 | 节点与具体自动机分离；蓝图与运行现场分离；模型提出计划、程序执行规则 | 所有中断都走服务器与恢复器；替换父节点是通用恢复方式；必须先建通用调度树 |
| [上下文订阅](./context_subscribe.md) | 如何持续获得变化对象的当前信息 | 当前观察不必永久堆积在模型对话里 | 末尾注入必然改善缓存；刷新本身就保证信息足够新 |
| [响应式 Agent](./react_agent.md) | 如何由外部变化推动运行 | 外部事件成为一等输入；等待与推理分开 | 收到事件就必须分叉上下文；锁可以在并发结构完成后再考虑 |

尤其值得注意的是，后两篇已经在修正第一篇的隐含前提：系统必须记住的东西，超过了下一次请求应该发给模型的东西；系统必须接收的输入，也超过了模型主动请求的工具结果。

因此，第一篇可以继续作为模型适配层的起点，但不宜继续充当整个 Agent 的状态模型。

## 3. 分层：既有纵向职责，也有横向选择

建议按职责理解系统，而不是立即按 crate、类或元组分拆。

| 层次 | 主要回答的问题 | 应包含的内容 | 与原构想的对应 |
| --- | --- | --- | --- |
| 任务规格与评价 | 什么算完成、正确、值得运行？ | 目标、成功谓词、预算、验收条件 | 原文较缺少，需要补充 |
| 单个 Agent 的控制语义 | 一个执行过程下一步做什么？ | 状态、输入、控制转移、动作、完成与失败 | 智能自动机、ReAct、Workflow、SMD |
| 观察与上下文构造 | 这次模型调用能看见什么？ | 历史选择、资源快照、工具可见性、预算内渲染 | API 建模、上下文订阅、多槽 Prompt |
| 调度与协作 | 哪个任务何时可以运行？ | 收件箱、等待、唤醒、子任务依赖、取消、并发限制 | 响应式 Agent、调度树、中断处理 |
| 外部能力与适配 | 如何与实际模型和环境交互？ | 模型 API、文件、计时器、CI、MCP、工具执行 | ModelProvider、Tool、事件源 |
| 产品装配 | 为哪类用户提供什么能力？ | 领域配置、界面、模型选择、允许的能力 | 发行版 |

Lean 不是额外的一层。它可以描述其中若干层的规则以及层间契约，并证明这些规则的性质。日志、测量和预算也会跨越多个职责。

原来的 Runtime / Host / 发行版仍可以保留为工程边界，但应允许调整：

- Host 实现具体控制语义、上下文构造、能力适配和节点包装。
- Runtime 管理节点、输入投递、调度阶段、等待与唤醒，执行确定的协议规则。
- 发行版选择任务、能力、策略和用户体验。

**“Runtime 不解释任务内容”成立；“Runtime 与理论基本无关”不应成为原则。** 唤醒、取消、替换、结果归属都是可以形式化且值得验证的语义。机械执行仍然具有协议语义，只是不负责理解“登录按钮为什么不可点击”。

另外，ReAct、Workflow、事件驱动、多槽上下文不全是同一条轴上的替代品：

| 设计维度 | 可选策略示例 |
| --- | --- |
| 控制流 | ReAct、线性 Workflow、显式状态图 |
| 信息构造 | 完整历史、选择性历史、资源快照、按状态切换上下文 |
| 激活方式 | 请求启动、定时启动、事件唤醒 |
| 协作方式 | 单 Agent、固定子任务、动态委托 |
| 并发方式 | 串行处理、隔离分支、受控共享写入 |

一个 Agent 完全可以同时是“内部使用 ReAct、每次调用刷新文件快照、外部由 CI 事件唤醒”。不需要为每种组合先发明一个全新的自动机谱系。

## 4. 最关键的拆分：历史、观察、请求、事件

建议明确区分以下对象：

- **执行记录**：发生过的模型调用、工具调用、事件、控制决定与使用过的观察版本。
- **模型对话历史**：从执行记录中保留或选出的、符合模型交互协议的消息序列。
- **当前观察**：一次采样得到的资源内容及其版本、时间和读取状态。
- **本次请求**：由控制状态、选定历史、当前观察、工具可见性等构造出的模型输入。
- **收件箱**：已经到达但尚未被当前执行过程处理的输入。

它们可以共享存储，但不能在语义上视为同一个东西。

设当前控制状态为 $q_t$，模型对话历史为 $H_t$，内部数据为 $D_t$，观察订阅集合为 $U_t$，环境为 $E_t$。一次请求可以描述为：

$$
O_t=\operatorname{observe}(E_t,U_t),\qquad
C_t=\operatorname{render}(q_t,D_t,H_t,O_t).
$$

随后才有：

$$
G_t\sim\operatorname{Gen}(\text{Model},C_t).
$$

这里的观察应带版本或采样时刻。多个资源逐个读取，不自动构成同一时刻的原子快照；是否需要跨资源一致性，是另一个要明确的条件。

“调用前刷新”也只保证观察来自某个采样点，不保证模型完成推理或执行动作时它仍然最新。对依赖资源版本的写入，应在提交时重新检查前提。上下文订阅改善观察过程，不会消除观察与行动之间的时间差。

### 4.1 上下文订阅与事件订阅要有不同的契约

**上下文订阅回答：“下一次推理之前，刷新什么？”**

**事件订阅回答：“出现什么变化时，安排一次处理？”**

文件可以加入上下文订阅，但它改变时不一定唤醒 Agent；一个 CI 完成事件可以唤醒 Agent，但没有必要把全部 CI 日志永久加入所有后续请求。同一个资源也可以同时提供这两种能力。

熔炉场景可以拆为：烧制完成事件唤醒任务；开始下一次推理前，重新取得库存与熔炉状态。事件说明“有事发生”，快照说明“现在是什么情况”。延迟到达的事件不能代替当前观察。

### 4.2 “不再发送旧快照”与“删除旧证据”不同

你的上下文订阅方案确实可以减少重复读文件的对话片段。但是，如果某次模型决定依赖文件版本 v7，后续只保留 v8，系统就失去了检查该决定依据的材料。

建议保留每次调用使用的观察版本与可恢复内容，后续请求只发送需要的当前版本。内容寻址、快照引用等具体实现可以以后再选；契约先明确。

还需要一个历史处理策略：模型曾经根据旧快照说出的判断，不会随着快照替换而自动失效。请求中应标明版本和变化，必要时选择性保留历史。工具调用及结果配对也不能为了“去噪”而随意破坏。

### 4.3 缓存收益是待测假设

“稳定内容在前、易变内容在后”有合理依据，但不能推出所有缓存都会保留。以 Claude 的官方说明为例，缓存基于请求前缀，并受内容层次、断点等条件影响。[来源：Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

对于你提出的策略，假设前一次请求为：

$$
C_t=H_t\Vert O_t,
$$

而下一次是：

$$
C_{t+1}=H_t\Vert G_t\Vert R_t\Vert O_{t+1},
$$

其中 $R_t$ 是工具结果，$\Vert$ 只表示概念上的连接。那么两次请求通常从旧 $O_t$ 所在位置开始分歧。稳定的 $H_t$ 有复用机会，但不能保证旧快照及其后的计算复用。实际编码是否保持同样的公共前缀，还取决于提供方适配。

因此应同时测量重复上下文大小、缓存读写量、总 token、延迟和任务效果。每次刷新整个大文件，也可能比按需读取更昂贵。上下文订阅的价值首先是观察管理更清晰，其性能收益需要证据。

## 5. 响应式执行不要求立即分叉上下文

[响应式 Agent](./react_agent.md) 中最重要的能力是外部事件能够驱动任务。“分裂一个上下文，再进行整合”只是实现这一能力的一种并发策略，不应成为它的定义。

建议第一版采用：**每个逻辑 Agent 有一个收件箱，同一时刻只有一个活动推理过程，在规定的安全点处理新输入。**

- Agent 正在等待：相关事件到达后使它可运行。
- Agent 正在模型调用或工具执行中：事件进入收件箱；当前操作完成后再处理。
- Agent 已终止：按明确规则拒绝、记录或转交事件；不默认复活。
- 高频事件：按种类选择排队或合并，不能把所有事件都当成可覆盖的“最新状态”。

这已经能支持熔炉、群聊消息和 CI 结果三个例子的核心需求。收到输入与立即发言也是两件事：群聊消息可以排队或批量处理，模型可以选择不产生对外动作。

原文中“ReAct 只能轮询”“MCP 本质上半双工”的判断需要收窄。ReAct 描述的内部循环，不决定外部宿主是否可以等待异步结果；把某个平台只包装成查询工具，是一种接入方式，不是协议能力的普遍边界。至少在 MCP 2025-06-18 资源规范中，就已有可选的资源订阅与更新通知；是否进一步唤醒 Agent，仍需宿主实现。[来源：MCP Resources](https://modelcontextprotocol.io/specification/2025-06-18/server/resources)

### 5.1 分叉真正增加的是提交问题

如果以后保留上下文分叉，需要分别定义：

1. 分支基于哪个状态与观察版本建立？
2. 分支是否可以执行有副作用的工具？
3. 分支输出是建议、补丁，还是已经执行的操作？
4. 主执行过程已发生变化时，分支结果怎样检查并提交？

把两个分支的文字合并，不能撤销已经发送的消息，也不能自动解决代码补丁冲突。读写锁只能约束特定资源的访问；如果模型在读锁释放后才提出写操作，其依据仍可能过期。

因此建议把这个想法命名为“推理分支与结果提交”，先实验只读分支，或让分支只产生待检查的计划。要允许共享写入，资源身份、版本检查和提交规则就必须同时进入设计，不能全部留到以后。

## 6. Layer Cake：保留边界，缩减强制流程

### 6.1 区分控制状态、调度状态和调度阶段

原来的 $q$ 可以表示“定位问题”“修改”“检查”等任务状态；Running、Suspended、Exited 是对外暴露的生命周期。它们不必一一对应。

但只有生命周期和节点角色，还不足以唯一决定全部调度行为。一个 Suspended 的工作节点没有孩子，可能表示：

- 刚提出请求，还没创建中断服务器；
- 服务器已经返回空的前置任务集合，正在准备恢复；
- 前置任务已结束并被移除；
- 节点在等待外部事件。

这些情形不能靠同一个“Suspended 且无子节点”条件区分。否则同一条规则可能重复启动服务器，或者误把普通等待当成能力不足。

补充办法不是一定要增加公开生命周期枚举，而是保存足够的调度阶段、等待原因和请求标识。生命周期可以继续是投影，协议状态不能丢失。

### 6.2 等待与重构应当分开

| 情形 | 建议的默认处理 |
| --- | --- |
| 等待一个已启动的 CI 作业 | 记录作业 ID，等待完成事件 |
| 等待一个资源可用 | 登记等待条件，收到通知后重新检查 |
| 当前上下文中的文件快照过时 | 刷新观察，必要时重新评估计划 |
| 缺少允许且可补充的工具 | 经过配置检查后补充能力，或构造后继实例 |
| 任务需要其他工作先完成 | 显式委托并等待结果 |
| 原执行结构已不适合任务 | 执行有条件的重构或替换 |

“每次中断都启动一个服务器和一个恢复器”把这些情形捆绑得过紧。获取一个已知结果不一定需要新增两段模型推理，也不一定需要替换父节点。

保留中断服务器与恢复器作为 Host 可选策略；先不把它们定为 Runtime 唯一的恢复协议。它们可以由模型、确定性程序或二者组合实现，选择依据是实际决策需求。

### 6.3 替换节点之前，需要定义身份与结果归属

响应式执行会让旧节点在被替换后仍收到工具结果或通知。建议区分稳定的逻辑任务 ID 与每次运行实例的 generation/epoch：

- 逻辑任务 ID 用于持续的用户目标、父子关系和事件路由。
- 实例 ID 用于某次执行的上下文、在途调用与结果关联。
- 替换动作必须说明哪些订阅、预算、结果和待处理事件被继承。
- 旧实例的迟到结果不能无条件写入新实例。

这不等于现在就要实现完整持久化系统；即使在内存 MVP 中，也应该让这些归属在类型或记录中可见。

### 6.4 树适合管理所属关系，但不必承载所有通信

父任务创建子任务，适合用树表示所有权和清理责任。CI、Reviewer、Manager 之间的通知，则可能跨越这棵树。

可以保留任务树，并另外使用事件路由与任务标识表达通信。不要为了一个跨节点通知，强行改变父子关系，也不必为了未来所有依赖，立刻把调度器扩展成通用图执行引擎。

### 6.5 蓝图的边界值得保留，但先用配置代替语言

“蓝图是从 DSL 到实例的解释器”是清楚的长期方向。第一版只需要一个有类型的配置构造器，规定：模型、工具、观察项、预算和控制策略。

等第二、第三种真实实例出现后，再判断哪些参数值得抽成 DSL。脚本形式的任意转移函数、WASM、多谱系插件和通用序列化都先推迟。

最大步数等局部预算可以放在蓝图中，但系统级预算不能只依赖它。否则每次重构或委托都可能重新获得一份局部预算。应由共同的预算账户限制整个任务的资源，并明确保留或扣除规则。

## 7. API 与工具建模：要补充的不是更多字段，而是不同对象之间的关系

### 7.1 把模型请求视为一个受支持子集

[API 建模](./llm_api_model.md) 的结构适合作为“文本与工具调用”这一子集的内部表示。对于“与三个 API 一一映射”的主张，当前文档没有定义完整的映射、逆映射和所支持的特性范围，因此尚不能支持这个结论。

建议改为：定义本项目需要的共同能力；适配器明确报告支持、不支持或会丢失的信息。暂不追求完整覆盖所有提供方。

当前结构还有几个可以直接从字段发现的缺口：

- 它没有表达模型选择和生成配置，因此更像输入上下文，而不是独立完成调用所需的全部请求信息。
- `GenerateResponse.message` 若语义上必定是模型消息，宜使用对应类型，避免允许用户消息、工具消息混入。
- 网络或鉴权失败可能根本没有模型响应，宜由调用结果的成功/失败分支表达，不必强塞进生成停止原因。
- 工具执行失败应与模型调用失败分开；模型生成结束也不等于任务成功。

所以，“没有 Tool Use 就退出”可以保留为某种 ReAct 策略，但必须先排除截断、调用失败等情况，并说明普通文本回答是否就满足该任务的完成条件。

### 7.2 工具分类应拆成两个维度

原文的上下文注入、状态转移、自省并不是互斥的同一级分类。自省通常也是读取；写文件、发送消息则有外部副作用，不能仅理解为追加一段返回文本。

建议分别描述：

- **效果**：读取信息、改变外部资源、发出控制请求。
- **用途或可见性**：工作工具、自省工具、领域工具，以及哪些状态允许调用。

模型调用控制工具时，可以返回类型化意图，再由控制器统一更新状态、消息和日志。工具不必因此持有整个格局的可变引用。

工具的可见集合还应与执行时的允许集合区分：请求里没有展示某个工具，并不等于执行器已经禁止它。模型提出的名称、参数和状态转移意图，仍应由程序按当前配置检查。

一次输出包含多个工具调用时，还需要规定执行顺序；如果同时出现写入、等待和退出意图，不能由异步完成顺序偶然决定语义。MVP 可以限制为顺序执行，并明确控制意图的处理位置。

“全局记忆不做成 Tool”则属于可选策略。对短任务，启动时读、结束时写可能够用；对长期运行任务，什么时候刷新与提交记忆需要重新定义，不能由自动机理论直接决定。

## 8. 数学切入口：把隐藏在 δ 里的交互拆成可检查的事件与命令

不建议现在继续增加一个包罗万象的大元组。先保留现有自动机作为局部控制模型，再为交互补一个小协议。

一种可探索的形式是纯的状态更新函数：

$$
F:S\times I\longrightarrow S\times\operatorname{List}(A).
$$

其中：

- $S$：包含控制状态、内部记忆、等待条件、在途请求和剩余预算的内部状态；
- $I$：外部事件、观察结果、模型返回、工具返回等类型化输入；
- $A$：请求观察、调用模型、执行工具、登记等待、完成等命令。

外部执行器执行命令，随后把结果作为输入送回。模型生成和工具副作用因此不再隐藏在纯函数 $F$ 内。这里的状态、输入与命令只是建议的职责划分，字段应由最小用例逐项确定。

模型请求由显式的上下文构造函数生成；外部环境可以自行变化，不应假设它只在工具调用后变化。第一阶段把模型返回看成任意合法输入即可，不需要马上引入概率。

与原五元组的关系是：把原来集中在 $\delta$ 内的解析、控制决定、上下文更新与外部交互分开，使中途等待和输入到达可以被表达。将一轮外部交互压回一个大步骤，可能恢复原来的抽象视图；但对应关系需要定义观察对象后再证明，不能仅凭外形相似宣称等价。

当前 [Basic.lean](../AgentTheory/Basic.lean) 有意使用纯转移、显式抽样输入，并把退出设为吸收态。这是一个清楚的基线，建议保留。它没有给抽样输入指定概率分布，也没有限制 State 必须有限，更没有形式化工具副作用、挂起或事件。

原文的线性 Workflow 还应与这一运行约定对齐：如果把最后一个任务状态直接当作退出态，进入它时就停止生成或处理，最后一个任务可能被跳过。现有 [Workflow 示例](../AgentTheory/Examples.lean) 已经使用独立退出态解决了这个问题；后续规格应沿用这个明确约定。

建议在后续实验中另立交互模型，通过具体实例和模拟关系连接旧定义，而不是现在把现有类型一次性改到能容纳所有设想。

### 8.1 最先值得证明的性质

下面都是候选性质，尚未在本项目中形式化或证明。它们需要根据最终规则精确定义。

| 候选性质 | 必须说明的条件 | 能帮助避免什么 |
| --- | --- | --- |
| 一个 Agent 至多有一个在途模型调用 | 所有调用都经过同一启动规则，返回按请求 ID 配对 | 重复唤醒启动多次推理 |
| 等待期间不主动生成 | 没有匹配事件、取消或超时输入 | 用模型调用维持空转 |
| 旧实例结果不改变新实例现场 | 结果携带实例标识，输入规则检查归属 | 重构后的迟到结果污染 |
| 同一上下文槽只渲染一个选定版本 | 固定观察输入，渲染器按槽选择 | 新旧资源快照无界叠加 |
| 整体预算不因委托或重构增加 | 预算由公共账户管理，每次派发计费 | 局部步数上限被递归绕开 |
| 终态不再派发动作 | 终态定义与取消完成规则明确 | 完成后重复调用工具 |

例如，“至多一个在途调用”可以写为不变式：

$$
\forall a,\quad |\operatorname{inFlightModelCalls}(a)|\le 1.
$$

证明工作是说明初态满足它，且每一种输入转移都保持它，而不只是把它写成字段注释。取消时如果外部调用仍在运行，也必须计入状态，不能仅删除句柄便认为性质成立。

“事件到达后最终处理”属于活性性质，还要假设调度公平、所需操作会返回、节点没有被取消等；不能仅从队列的存在推出。重复事件下“不重复产生副作用”，也不能只靠接收端去重推出：外部写入成功但确认丢失时，需要额外的幂等或查询机制。

### 8.2 暂时不要求 Lean 回答什么

第一阶段不要求证明 LLM 总能完成任务、某种上下文组织一定更聪明、重构必然改善结果，或所有 Agent 架构计算能力等价。

任务正确性可以先由关系 $R(x,y)$ 描述，不要求立刻拥有判定它的程序。可执行检查器是另一个对象；测试通过、模型宣称完成和真正满足规格需要区分。

形式化能先约束“模型无论返回什么，外围机制都不会违反哪些规则”。它不能替代对真实模型效果的实验。Lean 中的协议证明也不会自动覆盖 Rust 实现、API 适配器和外部环境；需要后续的实现对应、轨迹检查或其他验证证据。

### 8.3 一个比“结构等价”更有针对性的研究问题

在相同任务、模型和预算下，比较“重复 read 加历史堆积”与“按轮刷新快照”的表现：上下文长度是否更可控，模型是否更少根据旧信息行动，延迟和成本是否改善？

这里可以证明的是渲染器的版本选择、记录保留和长度界等结构性质；需要实验的是模型成功率、响应质量与缓存收益。两者共同构成结论，比只证明两种 Prompt 都能编码成字符串更有用。

我上一轮提出的重试成功概率界仍然可以成为一个小型概率练习，但读完这四份文档后，我不把它放在你当前研究路线的首位。你反复遇到的问题更集中在观察、等待、身份和继续执行的语义。

## 9. 取舍清单

| 想法 | 建议 | 理由 |
| --- | --- | --- |
| 智能自动机的基本运行定义 | 保留为基线 | 已经清楚地区分生成、转移和退出 |
| 模型接口内部表示 | 保留并收窄 | 先支持真实需要的子集，不承担全运行时状态 |
| 请求前刷新资源观察 | 优先实验 | 四份构想中最具体、可独立测量的能力之一 |
| 外部事件、收件箱、等待与唤醒 | 优先实验 | 是三个响应式场景的共同需求 |
| Host 与 Runtime 的职责分离 | 保留原则，推迟通用框架 | 先靠明确函数边界即可，不必提前拆出插件系统 |
| 所有中断必须经过服务器与恢复器 | 取消强制，保留策略 | 普通等待不需要语义重构 |
| 空前置任务、递归服务器与恢复器 | 后置 | 在普通等待都未落地前，引入了过多协议阶段 |
| 上下文分叉与整合 | 后置 | 事件响应本身不需要并发分支 |
| 共享资源读写锁 | 随共享并发一起设计 | 不提前建锁框架，也不在并发实现后再补语义 |
| 蓝图 DSL、脚本转移、多谱系注册 | 后置 | 缺少真实实例约束时，容易把猜测固化成接口 |
| API 完整一一映射、缓存必然改善 | 撤回为待验证主张 | 当前定义与实验都不足以支持 |
| 全局记忆只在创建和退出时读写 | 降为配置策略 | 长期运行与事件驱动任务可能需要其他时机 |
| Layer Cake 通用发行版 | 暂停扩张范围 | 先验证一个能力闭环，再考虑产品覆盖面 |

这些取舍不是说后置的想法没有价值，而是它们应该由已经发生的需求引入。尤其不要把“理论允许这种结构”当成“第一版必须实现这种结构”的理由。

## 10. 第一个 MVP：一个 Agent、一个变化资源、一种唤醒事件

建议先用本地模拟的异步作业表达熔炉场景。它能展示观察与唤醒，不需要接入游戏、代码托管平台或真实多人协作系统。

**演示目标：Agent 启动作业后进入等待；作业完成使它重新运行；下一次推理收到完成后的资源快照，并执行后续动作。等待期间不调用模型。**

最小执行过程：

1. 任务“准备材料并完成后续制作”进入系统，产生稳定任务 ID。
2. Agent 获得资源 v0 的观察，调用启动作业工具。
3. 工具返回 job ID；系统登记带关联标识的完成通知与等待条件。
4. 等待前检查当前作业状态，处理登记前后已完成的情形，避免“完成发生在订阅之前”的丢失唤醒。
5. 作业完成，事件进入收件箱；Agent 变为可运行。
6. 系统刷新资源快照，将事件与快照一起用于下一次请求。
7. Agent 执行后续动作，记录结果并结束；重复完成事件不会再次触发同一后续动作。

第一步实现使用脚本模型和可控事件源，固定输入输出，以便复现顺序问题。这个阶段是运行协议原型；然后接入一个真实模型适配器，才检验完整 Agent 闭环。不要把脚本模型通过等同于模型能力已经得到验证。

验收至少覆盖这些情形：

| 场景 | 应观察的结果 |
| --- | --- |
| 完成事件正常到达 | 从等待进入下一次执行，关联 job ID 正确 |
| 事件在进入等待前到达 | 不永久等待，不遗漏已经完成的作业 |
| 同一完成事件重复到达 | 不重复启动同一后续动作 |
| 不相关作业的事件到达 | 不解除当前等待条件 |
| 模型调用过程中有事件到达 | 事件被排队，同一 Agent 没有第二个并发模型调用 |
| 资源在两次请求之间更新 | 后一次请求使用明确标注的新版本；前一次依据仍可查 |
| 等待超时、模型调用失败、用户取消 | 有明确终止或处理结果，不以普通成功退出掩盖 |

第一版可以仅在单进程内存中工作，不承诺进程崩溃后的恢复与外部副作用的严格一次执行。这里的事件去重保证应限于已实现、已测试的生命周期范围。

需要记录的指标很少：模型调用次数、等待期间调用次数、事件到处理的延迟、每次观察版本、上下文大小、任务是否完成。真实模型接入后再增加 token 与缓存计量。

这个 MVP 暂不包含多 Agent、自动生成蓝图、递归中断、上下文分叉、跨进程调度、通用锁服务或多模型适配。它保留了你后两篇最有辨识度的构想，同时给第一篇的接口和最初的自动机定义一个具体使用场景。

## 11. MVP 之后，按证据决定下一步

不要把剩余愿景排成一条必须全部实现的长队。让实验结果决定是否扩展。

| 已经确认的需求 | 下一步才值得增加的机制 |
| --- | --- |
| 单 Agent 刷新快照确实减少旧信息误用 | 更细的观察选择、差量或摘要策略 |
| 一项任务确实需要另一个任务先完成 | 固定的父子任务委托与结果收集 |
| 固定委托无法覆盖实际缺失能力 | 模型参与的中断规划与后继配置 |
| 串行事件处理无法满足明确延迟要求 | 隔离的推理分支，再设计提交规则 |
| 多种实例重复出现相同构造参数 | 提取蓝图配置或 DSL |
| 运行记录需要跨进程恢复 | 持久化、恢复协议与副作用去重机制 |

如果观察与唤醒已经解决大部分需求，Layer Cake 可以先是一个小型执行库。如果后来证明动态委托与重构不可缺少，再让它成长为你原先设想的框架。

## 12. 让数学帮助取舍，而不是增加启动工程的门槛

你不需要先建立完整的“智能理论”，才能开始做出有意义的形式化。对于当前这些构想，数学首先能提供三种帮助：

1. **迫使概念分开。** 等待不等于能力不足；输出停止不等于任务成功；信息刷新不等于事件触发；上下文合并不等于外部效果合并。
2. **暴露缺少的状态。** 两段历史在当前表示中完全相同，却需要采取不同动作，就说明表示或规则还不够。例如同样“挂起且无子节点”，却可能分别需要启动服务器、恢复或等待外部事件。
3. **给出带条件的保证。** 明确哪些性质来自协议，哪些依赖调度公平、外部工具或模型能力，而不把它们都归因于一个优雅的元组。

接下来的最小工作单元，可以固定为：一个场景、一组状态与输入、一个希望保持的性质、一个会破坏它的反例、一份可运行的轨迹。证明与实现围绕同一个问题推进。

四份文档可以在这里汇合：**由智能自动机描述局部控制，由上下文构造提供当前观察，由事件与调度决定继续执行的时机，由清楚的协议连接它们。** Layer Cake 是这些机制的一种工程组织；是否需要完整的递归重构架构，交给后续实例和实验回答。
